### Computer Use: input yang ditolak portal

- Gejala nyata dilaporkan pemilik: klik pada form Google di Brave Origin gagal, agent menulis "Klik via desktop tool ditolak D-Bus". Traceback di `/tmp/screen_err.txt` menunjukkan `GDBus.Error:org.freedesktop.DBus.Error.Failed: Session is not allowed to call NotifyPointer methods (0)` dari `input.py::_notify_motion`.
- Akar masalah: injeksi input punya dua jalur. Jalur portal `RemoteDesktop` ditolak karena sesi portal tidak memegang izin pointer/keyboard, sedangkan jalur kernel `uinput` tidak aktif karena `/dev/uinput` hanya `600 root:root` dan pengguna belum ada di grup `input`. Jadi tidak ada jalur input yang berhasil; capture tetap jalan, sehingga gejalanya tampak seperti "backend rusak" padahal izin.
- Perbaikan sistem di mesin ini: udev rule `/etc/udev/rules.d/99-uinput-ccode.rules` (`GROUP="input", MODE="0660"`), `/etc/modules-load.d/uinput.conf`, `modprobe uinput`, `usermod -aG input andikaputra`, plus `setfacl -m u:andikaputra:rw /dev/uinput` supaya berlaku tanpa logout. Bukti: `/dev/uinput` menjadi `660 root:input`, `uinput_backend.available()` mengembalikan `True`, dan `ensure_device(1920,1080)` berhasil membuat device. Jalur kernel dipilih otomatis pada aksi berikutnya (pemeriksaan izin dan bounds dilakukan per aksi), jadi aplikasi tidak perlu di-restart.
- Perbaikan kode di batas edit project: `services/desktop/ccode_fast_profile.py` menambah `install_input_fallback_policy` yang menerjemahkan penolakan portal menjadi pesan berisi dua langkah perbaikan (aktifkan `uinput`, atau beri ulang izin portal), ditandai `isError` supaya agent tidak mengulang perintah yang sama. File vendor (`input.py` dan lainnya) tidak disentuh. Tes regresi baru ada di `tests/test_desktop_profile.py::InputFallback` (penolakan pointer, penolakan keyboard, dan error tak terkait tetap menyebar).
- Dokumentasi: langkah perbaikan ditulis di `docs/OPERATIONS.md` (bagian **Computer Use: klik/ketik ditolak**), jalur input ganda dijelaskan di `docs/ARCHITECTURE.md`, dan release notes 1.0.0 di GitHub diperbarui dengan prasyarat yang sama supaya pengguna lain tidak menebak-nebak.
- Kejelasan UI: baris terakhir panel Settings → Computer Use kini menyebut bahwa sakelar itu adalah entry `linux-desktop` yang sama dengan yang tampil di **Settings → MCP Servers** ("same backend, one state, either switch works"), supaya tidak jadi pertanyaan "yang mana yang dipakai". Tidak ada sakelar yang ditambah/dihapus, tidak ada komponen baru; hanya teks. Alasan tidak menyembunyikan barisnya: daftar MCP itu generik untuk semua server, dan panel sendiri menyimpan hal yang tidak ada di daftar (status + jumlah tool, petunjuk izin, pintasan kotak chat).

### Rencana kerja rilis Windows

- `windowsrelease.md` mencatat rancangan rilis Windows x64 dengan fitur yang sama seperti rilis Linux 1.0.0: tanpa akun, namespace sendiri, provider BYOK + 9Router, 12 command, 32 skill, 12 subagent, Token savers, Activity, MCP katalog, Marketplace + n8n, backup/restore, dan Computer Use. Voice tetap dihapus.
- Fakta yang dijadikan dasar: vendor hanya menerbitkan `ZCode-3.14.3-win-x64.exe` (baseline kita 3.14.5 Linux), ASAR terpinsel memuat native linux-x64, seeding desktop digerbang `process.platform==='linux'`, `services/mcp/launch.cjs` menulis shim `/bin/sh` dan memaku ripgrep linux, `storage.py` memakai default `.local/share/ccode` tanpa cabang platform, dan feed update sudah dinetralkan.
- Computer Use Windows punya dua rute: helper bawaan vendor (kalau terbukti jalan tanpa akun dan tanpa feed vendor) atau backend MCP `windows-desktop` bergaya screen-mcp dengan tool sesingkat profil `ccode-fast` dan guard takeover yang sama. MCP dijelaskan sebagai transport, bukan kebutuhan khusus Linux; batas UIPI/UAC wajib ditulis, bukan diklaim setara Linux. Panel Windows tidak boleh menampilkan toggle tanpa fungsi.
- Installer Windows vendor (3.14.3) dibongkar untuk memastikan kelayakan: 143,1 MiB, SHA256 `815721ad…f3e5048b`; di dalamnya `resources/app.asar` (27.564 entri), native `win32-x64` (`conpty`, `pty`, `sshcrypto`), agent 16,7 MB di `resources/glm/zcode.cjs`, `resources/tools/{ripgrep,ugrep}`, `icon_windows.png`, `tray_icon.ico`, plus `elevate.exe`/`UAC.dll` dari installer.
- Bukti penting: hampir semua anchor patch tidak ada di build Windows 3.14.3 (`Zu`, `AI`, `z9`, `Ft`, `VOn`, anchor registry agent), dan nama chunk/asset renderer berbeda — jadi seluruh lapisan patch harus dicari ulang untuk baseline Windows, bukan disalin. Artwork brand tetap cocok. Jalur helper Computer Use vendor hanya disebut di JS (tidak ada helper biner di tree aplikasi), sehingga rute itu wajib dibuktikan di Windows sebelum dipakai.
- Rute vendor ditutup sebagai rencana utama: build Windows 3.14.3 tidak mengirim plugin `computer-use` sama sekali (hanya `browser-use-plugin`, `bundled-skills`, `node-repl-host`), tidak memuat paket producer di ASAR, mencari producer yang sudah terpasang di `<ZCODE_HOME>/computer-use/...`, dan mematikan probe screen-capture-nya sendiri (`shouldRunCuaScreenCaptureProbe(){return !1}`). Di Linux plugin itu ada tetapi eksekutornya juga tidak terpasang. Jadi rencananya backend sendiri: MCP `windows-desktop` bergaya `linux-desktop`, dengan tool sesingkat profil `ccode-fast` dan policy takeover yang sama.
- Rencana dimatangkan (2026-10-16): ditambah **daftar keputusan yang belum diambil** (K1 versi dasar, K2 lokasi namespace, K3 penjadwal model-sync, K4 runtime Computer Use, K5 strategi payload MCP, K6 lingkungan uji, K7 signing) dan **urutan milestone** M0–M5 dengan kriteria lulus per tahap, supaya kegagalan ketahuan di awal dan fitur tidak dihapus diam-diam saat porting.
- Fakta baru yang diverifikasi untuk Windows: paket MCP win32 tersedia di npm dengan versi yang sama seperti pin Linux (`@sdsrs/code-graph-win32-x64@0.169.0`, `@vscode/ripgrep-win32-x64@1.18.0`); `makensis` belum terpasang di mesin build (prasyarat M4); binary `rtk` yang ada lokal adalah build Linux, build Windows-nya belum terverifikasi.
- Temuan yang mengubah bentuk pekerjaan (2026-10-16): shell kedua build memakai Electron yang **sama** (`Chrome/146.0.7680.80 Electron/41.0.3` di Linux kita dan di installer Windows vendor), dan native-nya juga sama versi (`node-pty` 1.1.0, `ssh2` 1.17.0, node_module_version 145). Jadi rute terpendek jadi **hibrida**: pertahankan lapisan aplikasi 3.14.5 yang sudah dipatch, ganti shell-nya menjadi berkas Windows vendor, dan tukar dua native unpacked (`win32-x64/{pty,conpty,conpty_console_list}.node` + `sshcrypto.node`). Ini melewati pekerjaan mencari ulang seluruh anchor patch. Prasyarat kecilnya: `scripts/asar.py` perlu bisa **menambah** entri (conpty belum ada di ASAR Linux), bukan hanya mengganti isi.
- Rekomendasi keputusan lain dicatat di dokumen: namespace `%LOCALAPPDATA%\CCode` (K2), Task Scheduler per-user (K3), backend Computer Use berbasis Node + helper PowerShell agar Windows tetap ringan (K4), payload MCP per platform di repo yang sama (K5), PC Windows pemilik sebagai lingkungan uji (K6), unsigned dulu (K7). Semua masih menunggu persetujuan pemilik; belum ada kode Windows yang diubah.

- Verifikasi: `sha256sum -c SHA256SUMS` OK untuk ketiga artifact. AppImage dijalankan lewat FUSE pada root terisolasi: workspace terbuka tanpa layar login, `/` menampilkan 12 command, 0 error renderer. RPM dipasang ke root sementara (`sudo rpm --root … -i --nodeps --noscripts`): 21.323 entri (18.523 berkas), izin terbaca seluruhnya, tanpa state lokal, dan aplikasinya berjalan dari hasil instalasi dengan hasil yang sama.
