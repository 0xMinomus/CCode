### Perbandingan ukuran: apel vs jeruk

- Pengguna menanyakan baris "Disk footprint" di README: apakah CCode lebih berat dari ZCode? Ternyata baris itu membandingkan dua hal berbeda — 195 MB itu berkas AppImage upstream (squashfs terkompresi), sedangkan 653 MiB itu direktori CCode yang sudah diekstrak.
- Diukur langsung: AppImage 3.14.5 diekstrak (`--appimage-extract`) = **683.835.082 B / 654 MiB / 624 berkas**; direktori CCode terpasang = **682.637.475 B / 653 MiB / 624 berkas** → CCode **~1,1 MiB lebih kecil**, bukan lebih berat. Selisih terbesar: aset ikon CCode 218.316 B (1024 px launcher), 218.316 B (`icon_windows.png`), 170.502 B (`icon.png`), 124.923 B (`icon_512x512.png`) = −732 KB total, plus `app.asar` −169.756 B karena permukaan akun/cloud dibuang. Jumlah berkas sama (624 vs 624), jadi tidak ada berkas hilang di proses patch.
- README diperbaiki: satu baris menyesatkan diganti dua baris — **Distribution size** (AppImage vs paket yang belum ada) dan **On-disk footprint (unpacked, measured)**, plus catatan bahwa AppImage = squashfs terkompresi sehingga 195 MB mengembang jadi ~654 MiB bila diekstrak.

- Default branch `0xMinomus/CCode` dipindah dari `main` (upstream) ke `ccode-workspace`, supaya README CCode yang tampil di halaman depan repo, sementara label *forked from zai-org/ZCode* tetap. ### Fork resmi: CCode (fork) + CCode-archive (workspace)

- Repo workspace ini di-rename `0xMinomus/CCode` → **`0xMinomus/CCode-archive`**, dan **`0xMinomus/CCode`** dibuat sebagai fork dari `zai-org/ZCode` (Apache-2.0) lewat `gh repo fork`. Fork membawa history upstream; snapshot workspace ini didorong sebagai branch `ccode-workspace` supaya spesifikasi perilaku tetap bisa dirujuk dari repo rilis.
- Remote lokal dirapikan (`origin` = workspace, `fork` = repo fork, `upstream` = `zai-org/ZCode`), dan integritas diverifikasi: tree hash branch yang didorong identik dengan HEAD lokal, jadi tidak ada file yang hilang/berubah saat pindah.
- Catatan URL: karena nama `CCode` dipakai ulang oleh fork, redirect URL lama tidak lagi menunjuk arsip — semua dokumen memakai URL eksplisit (`CCode-archive` vs `CCode`).

Verifikasi pindah: tree sama di lokal/`origin`/`fork` (147 file, commit `bb823ee`), `git fsck` bersih.

### Harness lebih ringan: flag memori terukur, warmup malas, sisa kode dibuang

- `scripts/run.sh` menyalakan `--enable-low-end-device-mode` secara default (`ZCODE_MEMORY_FLAGS=0` mematikannya). Diukur pada root terisolasi saat idle dengan PSS: **876 MB → 748 MB** (15%, dua kali baseline 876,0 dan 873,9 MB), sementara DOM identik (judul, 19 tombol, 24 div, teks onboarding sama) dan log bebas `Unknown channel`/`No handler registered`/`ReferenceError`/`TypeError`.
- Flag lain diuji dan ditolak karena tidak terbukti atau berisiko: `--js-flags=--max-old-space-size=512` hanya 2 MB dan menahan pertumbuhan heap berisiko OOM, `--process-per-site` tidak memberi keuntungan, sedangkan `--disable-features=...` bisa menimpa daftar milik aplikasi sendiri.
- MCP desktop tidak lagi memuat model OCR/OmniParser saat start. `grounding.warmup` hanya prefetch (sesi dibangun lazy lewat double-checked lock di `ocr_boxes`/`_omni_session`), jadi melewatinya menghemat sekitar 60 MB per sesi MCP yang tidak berobservasi; `ZCODE_CUA_WARMUP=1` mengembalikan prefetch.
- Sisa yang dibuang: dua salinan pra-patch yang tidak dirujuk siapa pun (`services/desktop/server.py.before-zcode-fast`, `services/voice/worker.py.before-bilingual`; isinya tetap ada di riwayat git) dan satu import mati (`hashlib` di `services/model-sync/sync.py`). Scratch `runtime/check` (19 MB, dibuat ulang oleh `scripts/check.py`) dan seluruh root uji `/tmp/zroot-*` dihapus.
- Yang diperiksa dan ternyata bukan beban: cache Chromium di namespace standalone hanya 6,9 MB (tidak ada `Cache`/`Code Cache`/`GPUCache` yang menumpuk), CPU idle seluruh pohon proses sekitar 1%, dan timer model-sync 0,17 sampai 0,25 detik CPU dengan 60 MB transient per menit.
- Batas: angka berasal dari peluncuran terisolasi tanpa task, bukan sesi kerja panjang; memori saat tugas berjalan (renderer + MCP + task) belum diukur. `tests/test_desktop_profile.py` bertambah 2 tes untuk kebijakan warmup (116 → 118 tes).

### Computer Use Linux: jalur teks, klik per elemen, dan pointer yang tidak mudah menghentikan task

- `services/desktop/zcode_fast_profile.py` diperluas tanpa menyentuh file vendor. Permukaan tool naik dari 10 menjadi 15: ditambah `screen_read_text`, `screen_wait_text`, `screen_verify`, `screen_sense`, dan `screen_focus`; tool yang menulis lebih jauh (`screen_read_page`, `screen_read_selection`, `screen_tour`, `screen_reload`) tetap tidak diekspos.
- Model sekarang diarahkan ke jalur murah dan akurat: `screen_read_text` untuk melihat keadaan sebagai teks plus id elemen, klik dengan `element=<id>` (server menyelesaikan koordinat dan menolak id dari view lama), Set-of-Marks lewat `annotate=true`, cache elemen `use_cache`, dan crop `region` untuk teks kecil.
- Gambar pasca-aksi dilewati bila SENSE menyatakan frame tidak berubah; teks aksi dan petunjuk no-op tetap dikirim, jadi aksi no-op tidak lagi membayar token gambar. Mode tunggu perubahan menjadi `hybrid` (event damage dengan lantai poll).
- Kebijakan pointer: guard takeover dibungkus hysteresis berbasis jendela sampel. Kursor yang berhenti di tempat lain dianggap idle dan aksi tetap berjalan; pengendalian berkelanjutan selama `ZCODE_CUA_TAKEOVER_MS` (default 2500 ms) tetap membatalkan aksi dengan pesan `STOPPED`, dan `force=true` tetap tidak boleh dipakai melawan pengguna.
- Verifikasi: 19 tes baru di `tests/test_desktop_profile.py` (jendela pointer, pemasangan kebijakan, permukaan tool, default pasca-aksi, aturan lewati gambar) hijau lewat `make test`. Tes menangkap satu bug nyata (`except ... as` yang ter-unbind, membuat reraise gagal). Server asli via `services/desktop/bin/screen-mcp`: `initialize` + `tools/list` mengembalikan 15 tool dengan deskripsi baru, `tools/call screen_sense` dan `desktop_open_app` (nama tidak ada) berjalan tanpa portal; import nyata menunjukkan `policy=zcode-fast-hysteresis`, `shot policy=zcode-fast-noop-skip`, `WAIT_MODE=hybrid`.
- Batas: belum diuji pada desktop nyata (butuh portal dan pointer pengguna), jadi capture/OCR nyata dan efek kecepatannya belum diukur. Rincian, env knob, dan sisa pekerjaan di `docs/COMPUTER_USE_IMPROVEMENTS.md`.

- Kanal yang pemilik cloud-nya sudah dihapus kini dijawab lokal, bukan dibiarkan tanpa handler: remote connection SSH/WSL/Docker (`ConnectRemote`, `CancelPendingRemoteConnection`, `BindRemoteWorkspaceSessionContext`, `DisposeRemoteSession` → `{success:!1,error:"Remote connections are unavailable in the standalone build."}`/no-op), remote control (`StartWebRemoteControl`, `ResetWebRemoteControlPairing`, `StopWebRemoteControl`, `GetWebRemoteControlStatus` memakai bentuk kegagalan milik upstream sendiri: `reason:"unsupported-action"`, "Web remote control is disabled in this build."), serta preferensi auto-update. Sebelumnya renderer menerima `No handler registered` dan main mencatat `Error occurred in handler ...`.
- Dependensi lokal yang ikut terhapus di region registrasi IPC dikembalikan: `isDockerDaemonAvailable`, `listAvailableWSLDistros`, `listAvailableDockerContainers`, `listSSHConfigAliases`. Tanpa itu dialog SSH/Docker mengirim `TypeError: e.listSSHConfigAliases is not a function`.
- Guard build-time baru `cloud.guard_remote_ipc_dependencies` menolak build bila handler IPC memanggil `e.<service>` yang tidak dikirim ke `Ik()`; sebelumnya region registrasi yang diganti bisa menghilangkan provider lokal tanpa terdeteksi.
- Batas: fitur remote workspace (SSH/WSL/Docker) sendiri belum bisa dipakai pada varian standalone karena flow-nya memerlukan layanan client-config akun yang dihapus; melanjutkan fitur itu adalah keputusan terpisah (mengembalikan service tersebut atau membuat pengganti lokal), bukan bagian dari perbaikan ini.
- Verifikasi: `make build` + `make test` (33 tes) hijau; probe runtime pada root terpisah menunjukkan dialog Remote Connect (tab SSH dan Docker) terbuka tanpa `TypeError`, panel Mobile remote control menampilkan pesan "disabled in this build", penutupan jendela tetap bersih (`exitCode: 0`), dan seluruh log main bebas `No handler registered`, `TypeError`, serta `Unknown channel`.
